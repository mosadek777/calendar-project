# Constitution Audit (T-81)

**Audited against**: constitution **1.1.0** · **Date**: 2026-09-20
**Scope**: the delivered code — `backend\Scheduler.Api\`, `frontend\scheduler-app\`, and the
repository layout. Every check below was run against the code, not recalled from memory.

**Result: 1 open violation, 1 recorded waiver, 5 documentation drifts corrected during the
audit. Articles I, II, IV, V, VI, VII, VIII and IX all pass.**

---

## Article-by-article

### I — Ship Today · **PASS**

Built in the declared priority order. One story cut — **US-13**, the agenda screen — recorded
as a deliberate cut in `plan.md`, `tasks.md` Phase 9 and the stories matrix, with its cost
(FR-021, FR-022 unmet) stated. The P5 band in `spec.md` is marked conditional for exactly this.
Nothing was built that is not in a story.

### II — Documents Before Code · **PASS**

Phases 1–6 produced documents only; no source file exists before the Phase 7 approval commit.
Each phase ran in its own turn and stopped. Verifiable in the git history: the first code commit
is `5d2d4c0`, after six documentation commits.

### III — Fixed Repository Layout · **1 VIOLATION + 1 WAIVER**

| Check | Result |
|---|---|
| Repository root | `.gitignore`, `design-system.md` — the second is **waived**, see below |
| `specs\001-scheduler\` contents | as mandated, plus `checklists\` (pre-existing from Phase 2) |
| Backend folders | `Controllers`, `Services`, `Data`, `Models`, `DTOs` — **plus `Properties\`** |
| Frontend location | all React code under `frontend\scheduler-app\` |

**OPEN VIOLATION — `backend\Scheduler.Api\Properties\` is a sixth folder.** Article III names
exactly five. It holds `launchSettings.json`, generated by `dotnet new webapi` and tracked in
git. It configures the `dotnet run` profiles and nothing else — no application code.

Three ways to close it, developer's choice:

1. **Waive it** as framework-generated, the same way `Program.cs` and `appsettings*.json` are
   accepted at the project root by the plan's Structure Decision. One line in the waiver log.
2. **Delete the folder.** `dotnet run` then binds to random ports each start, and the CORS
   policy and the frontend's `BASE_URL` both hard-code `5233`, so this would need those pinned
   another way. Cheap to do, mildly annoying afterwards.
3. **Amend Article III** to permit framework-generated folders — not recommended: it loosens a
   rule that has otherwise held all project.

**RECORDED WAIVER — `design-system.md` at the repository root.** Accepted in writing by the
developer on 2026-09-20, scoped to that one file. See **Recorded waivers** in the constitution.

### IV — Boring Backend Architecture · **PASS**

- No `IRepository`, `UnitOfWork`, `IMediator`, MediatR, AutoMapper or CQRS anywhere — grepped
  across `.cs` and `.csproj`.
- Controllers are thin: every action binds a model, calls one service method, maps a result to a
  status code.
- All logic sits in four DI-registered services behind interfaces.
- **Every database call is `await`ed.** One `.ToList()` appears at
  `Services\AppointmentService.cs:44`, and it is **not** a violation: it is LINQ-to-objects over
  a list already materialised by `await ...ToListAsync()` on the line above. Noted here so a
  future reader does not re-flag it.
- Entity↔DTO mapping is hand-written (`ToResponse`).

### V — The DTO Boundary · **PASS**

No `User` or `Appointment` appears in any controller signature. Every request and response is a
DTO in `DTOs\`. `AppointmentResponse` deliberately carries **no** `UserId`. `AuthResponse`
carries only `Token` and `Email`, so `PasswordHash` is structurally unserialisable.

### VI — Identity and Ownership · **PASS**

| Check | Result |
|---|---|
| Passwords hashed | `PasswordHasher<User>`; verified with `VerifyHashedPassword`, never `==` |
| Plain password stored/logged/returned | never |
| `[Authorize]` on appointment endpoints | on the controller class |
| Identity source | `User.FindFirstValue("sub")`, 5 call sites, all in controllers |
| Client-supplied user id | **no DTO has a user id property** — nothing to spoof |
| Cross-user access | 404, never 403 — `Forbid()` and `Status403` appear nowhere |
| Signing key | `appsettings.Development.json` only, **not tracked by git** |
| Committed `appsettings.json` | contains no key, password or connection string |

### VII — Frontend Discipline · **PASS** (against 1.1.0)

Dependencies: `react`, `react-dom`, `react-router-dom`, `tailwindcss`, `@tailwindcss/vite`,
`radix-ui`, `shadcn`, `class-variance-authority`, `cn`, `tw-animate-css`, `react-day-picker`,
`date-fns`, `@fontsource-variable/geist`, **`lucide-react`**, **`framer-motion`**.

- No state management library — auth is a React Context, everything else local state.
- No component library or UI kit beyond shadcn/ui; no CSS framework beyond Tailwind.
- Day selection is shadcn's `Calendar` (react-day-picker) with a `busy` modifier. No hand-built
  grid; no FullCalendar or equivalent.
- `lucide-react` and `framer-motion` are the 1.1.0 allowances. **Motion is confined to the two
  permitted cases** — both presets live in `lib\motion.ts`, used by `App.tsx` (page transition)
  and `AppointmentList.tsx` (list enter/exit) and nowhere else.
- `@fontsource-variable/geist` is the package the amendment explicitly permits to stay.
- `components\ui\` was never hand-edited; the calendar is styled through `classNames` props.

### VIII — Email by Button, Never by Scheduler · **PASS**

- `IEmailSender` with one `SmtpEmailSender`, driven entirely by `IOptions<SmtpOptions>`.
- **No `IHostedService`, `BackgroundService`, `AddHostedService`, `Timer`, `PeriodicTimer`,
  Quartz or Hangfire anywhere in the backend.** Nothing in the solution *can* send mail except
  `POST /api/appointments/email-day`.
- The sender contains exactly one conditional — supply credentials when `UserName` is non-empty
  — and no provider name. The Gmail switch is configuration-only, documented in `plan.md`.

### IX — The Scope Fence · **PASS**

Grepped for every fenced item. No soft delete (`IsDeleted`/`DeletedAt` absent; delete is
`Remove` + `SaveChangesAsync`), no refresh or reset tokens, no email verification, no roles, no
recurrence, no pagination parameters, no background jobs, no test project, no Dockerfile, no
deployment configuration, no timezone handling.
